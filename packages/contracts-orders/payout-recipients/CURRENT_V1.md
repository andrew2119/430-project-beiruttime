# Private recipient v1

POST /internal/v1/payout-recipients changes the selected subject's synthetic recipient. GET /internal/v1/payout-recipients/operations/{operation_id} resolves a lost response. GET /internal/v1/payout-recipients reads the current version. These are additive adapter contracts, pending runtime registration.

All reads and retries require current subject or selected organization authority. A buyer role alone grants no access. Organization members require current recipient permission. Proof must bind actor, subject, organization, operation, method, reference and expected revision, with current verified contact, recipient verification and fresh second factor. Fresh means server time strictly before expiry and at most 300 seconds after issue. Equality expires. Proof references are opaque and never contain credentials.

Every response includes schema_version, operation_id, subject_id, watch_id, actor_id, organization_id, expected_revision, state, revision, pending_reason, next_actor and next_review_at. Recipient changes have no watch binding, so watch_id is null. Reads and unparsed requests have null operation_id and expected_revision; unresolved lookups have null expected_revision. Inapplicable organization and recovery fields are explicitly null. Pending results name the requesting actor as responsible for retrying the same operation and provide an authoritative UTC next_review_at 24 hours after the response. Retained receipts preserve the original expected revision. Success additionally returns recipient_version. Denied includes a stable code; unavailable is pending and retries the same operation. Conflicting operation reuse denies. Every decision is audited without recipient or proof bytes. A version is immutable. Transfer binding is once per transfer and cannot be overwritten; this module neither releases money nor owns balances. The Orders journal must consume that binding before release.

Persistence commits version, receipt and private outbox atomically. Adapters must obtain current authority and proof from the identity producer inside its serialized authorization boundary. Cached projections cannot authorize. Connected identity and journal integration remain required.
