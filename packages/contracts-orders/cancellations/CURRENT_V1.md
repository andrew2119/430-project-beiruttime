# Cancellation v1

Private `POST /v1/cancellations` accepts Command and returns Result.
Private `GET /v1/cancellations/operations/{operation_id}?subject_id=…` resolves a lost response and returns the current scoped cancellation view bound to the original operation. Immutable command receipts remain unchanged for exact retries. A missing operation is unavailable, never evidence of rejection. Retry the exact command and operation reference. Conflicting reuse returns 409; stale revision returns a retained denied result. Current permission is checked before every command, duplicate and lookup. Buyer requests are separate from assigned independent cancellation decisions. Consent withdrawal uses its own existing journey.

The provider must implement a bounded `transaction(command, principal)` context and scoped `lookup(subject_id, operation_id, principal)`. The transaction locks the canonical watch commitment and order in canonical lock order, refreshes payment attempts, quote, policy, work, parts, custody, refund reservations and current identity/assignment. Its `authorized(action)` checks current organization, record scope and decision independence. `facts` is validated as Facts. `receipt(operation_id)` and `save(command, principal, result)` bind the entire command, actor, organization, subject/watch, source revision and retained quote/policy. Conflicting reuse fails. `apply(result)` changes the canonical commitment or fulfilment hold only. Receipt, effect and minimal outbox insert commit atomically. Every accepted or pending cancellation blocks new work/dispatch and settlement while unresolved. Only safe unpaid acceptance may release, once; it does not relist stock. No balance or refund authority is added here.

Provider calls have a five-second total bound. A timeout returns unavailable and requires operation lookup or the identical retry. A producer may commit before response loss. Persisted results survive process restart. Missing providers fail closed. Pending cases name the responsible actor, 24-hour review and 48-hour escalation. A decision must re-read all source facts under the same lock, including a payment/work race. Request and decision have distinct stable operation references and expected revisions.

Paid acceptance pauses fulfilment for refund review; it is not completed cancellation. After dispatch or custody transfer, verified actual return of the correct watch, condition and accessories or an authorized recorded failure exception is required before refund eligibility. Job refundable basis uses retained accepted unperformed labor and unused returnable parts; completed work and consumed parts are excluded. The source validates those line allocations, and all pending and confirmed refunds count against the principal cap. Collected fees are never included. Full job refunds preserve the separate business fee receivable. Refund confirmation, actual return and final cancellation are distinct.

No public list, evidence, notes, preview or event payload is published. The provider emits only operation, subject and revision references into its private outbox. History reads require current scope, cursor pagination and server totals; no projection authorizes a command. The frontend uses private no-store reads, scoped by current access fingerprint and subject; only in-memory answers remain during refresh, and identity changes clear the form. Route composition and actual producer integration remain with their respective owners.

The supplied TransactionalProvider persists receipts and private outbox rows in one database transaction. Its injected canonical source exposes `lock(tx, subject_id, watch_id_or_none, principal)`, `authorized(tx, facts, principal, action)` , `apply(tx, facts, result)` and `current(tx, facts, original_receipt_result, principal)`. Current returns a validated Result view with the original operation, subject/watch, actor, organization and expected revision, but the latest aggregate revision, cancellation decision and money/custody follow-up. This lets a buyer see a later independent acceptance or decline without reading the decision maker’s private receipt. It does not execute an effect or alter the original receipt. Lock resolves and verifies the actual watch when lookup supplies no watch reference. Authorization rechecks current identity and record/business/assignment permissions, including revoked sessions and independent decision assignment; a prior authentication response alone is insufficient. Apply persists the cancellation state/revision and canonical hold or safe release under those locks. It must compare the exact source revision and prevent payment initiation, work, dispatch and settlement racing that hold. There is deliberately no default source that guesses these facts.

## Retained review timing

Facts require `hold_started_at`, `last_progress_at` (nullable authoritative UTC instants) and `escalation_actor` (the currently authorized escalation owner). An existing pending cancellation or accepted cancellation with unresolved payment must have a retained hold start; missing timing fails validation rather than starting another clock. The first held result supplies the server instant as `hold_started_at`. Apply persists it with the hold, revision, receipt and outbox in the same transaction. Later operations and process restarts load that original instant. Only recorded substantive progress may advance `last_progress_at`; a retry, lookup, new command, reassignment or unchanged review is not progress. Progress cannot precede the hold start.

The review deadline is the last recorded progress instant, or the original hold start, plus 24 hours. The escalation instant is that same anchor plus 48 hours. Equality is due: `review_overdue` becomes true at the review deadline and `escalated` becomes true at the escalation instant. An unchanged overdue hold keeps its original deadlines, including at 49 hours. Escalated results name `escalation_actor` as `next_actor`, retaining the original reason, hold and overdue deadline. The canonical source must route that responsibility and follow-up under the same lock; it must not substitute an ordinary owner or reset the clock. Current lookup views evaluate these timing fields against authoritative server time and retained progress so elapsed escalation remains visible without changing the immutable original receipt. A progress record can establish a new response/escalation deadline but never rewrites the original hold start.

Connected persistence, scheduled follow-up and escalation-owner routing remain owed with the canonical source integration; the supplied local cases establish the versioned boundary only.
