# Listing questions v1

Public list and suggestion reads accept a visitor with a null actor and organization; the authority callback must explicitly permit the current public listing scope. The host authentication callback returns null for an unauthenticated public request. All commands, operation lookups and private review require authentication. The host authenticates actor and selected organization from the current request, never from a submitted body. The authority callback rechecks current identity, membership, record scope, canonical watch and source revision on every read, write and retry. It returns `allowed`, `watch_id`, `revision`, `seller_id`, `can_ask`, `can_answer`, `can_report`, `assigned_moderator` and `assigned_question_ids`. A separate bounded assessment callback receives exact text and command kind. Absent publication assessment holds content; it never implies safe text. Publication assessment must cover abuse and private evidence as well as recognizable contact patterns. Attachments are unsupported.

The operation lookup and command routes are enumerated in `contract.json`. `index.ts` describes public responses. Commands reject unknown fields, oversized text, noninteger revisions and changed operation bindings. A stale command requires explicit review and a new operation; an uncertain command retains its exact body and reference. An identical replay returns the durable original result after current authority checks. A missing receipt is pending, never evidence of rejection. Question revision starts at one and increments for each accepted answer, report or moderation action. A duplicate question remains permitted after presenting matching answered questions. Normalization is Unicode compatibility normalization, case folding and whitespace collapse, scoped to the same listing.

Reports immediately quarantine the question and its answer. Only an independently assigned moderator may hide it, with a nonempty private reason and durable audit. No public endpoint exposes held text, reports, report authors or audit reasons. An author or seller can submit an `appeal` with a private correction reason and the held question revision. The assigned independent moderator reads question, reports and appeals through the private `review` operation; held content has no automatic public release. Public seller attribution uses the canonical seller identifier. Outbox rows contain only receipt references and states. The host must enforce restricted database access and bounded private retention.

The additive adapter has no runtime registration. The host supplies a durable database and a bounded current-authority callback. Each command atomically stores the question mutation, receipt and safe outbox record. The host owns dispatch delivery and service composition. This module neither allocates watches nor owns money or commercial authority.

The page read key is `listing-questions.v1`, listing and page, inside the shared access partition. Reads use the shared definition with zero freshness; current content remains visible during refresh. Warming is open-only because access must be current. Drafts, report reasons and exact pending commands remain in memory in the same mounted form across language changes; access changes discard that form. First-load placeholders use canonical shared primitives and the existing root shell. Destination registration, intent warming, page-table registration, measured page size and first-frame delivery require the shared composition owner. No delivery or phone measurement is inferred from these contracts.

Held-state assignment and support escalation are connected prerequisites: the local receipt deliberately has no invented assignee or review instant. The host must provide an actual responsible operator, next action, first response within 24 hours and escalation after 48 hours without progress before connected acceptance. The private appeal and assigned review operations preserve the handoff; they do not prove support delivery.

The shared sign-in return allowlist must admit `/questions` before intent resume is accepted; until then the existing sign-in helper uses its safe account fallback. Shared registration and this allowlist remain outside this module.

The `/questions` route declares its page, feature view and versioned read in `web/features/listing-questions/delivery-contract.json`. Its view uses the shared PageFrame, PageHeader and usePageRead composition. The shared access partition retains answers between visits and checks cancellation and current scope before accepting reads. Zero freshness preserves content during refresh; first-load placeholders appear only without an answer. Drafts and exact pending commands stay in the mounted form across language changes. Identity changes replace the form. Revoked moderation permission or a failed listing refresh clears retained private review content. Current assigned question identifiers also clear a reassigned question's retained private review.

Suggestion requests bind exact text and a zero-based page from 0 through 50000. Responses include the server total and requested page with up to 20 matches. Previous and next controls keep every matching answer reachable; paging never submits a question or changes its operation reference.

Private review accepts independent `reports_page` and `appeals_page` values from 0 through 50000, defaulting to zero. Each list returns at most 20 rows with its server total and requested page. Ordering uses descending creation instant and operation reference to keep tied instants deterministic. Paging rechecks current assignment and does not submit or replace a command reference.

Delivery declaration adoption by the shared validator and shell remains a foundation prerequisite. Shared route warming, arrival composition, measured page size and first-frame delivery remain owed. No delivery or physical phone measurement is inferred from local checks. After foundation adoption, rerun the interface rules and focused composition checks against the assembled source.
