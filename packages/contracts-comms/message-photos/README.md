# Protected watch photos v1

The operation table in `current.py` is the versioned HTTP lookup. `schema.v1.json` describes attachment commands. Uploads are bounded raw image bodies with operation, purpose and declaration query parameters. Only `watch_detail` and an explicit true declaration are accepted. JPEG, PNG and single-frame WebP decode to at most 12 million pixels and 5 MiB; the stored JPEG is independently bounded to 5 MiB. Re-encoding removes metadata, filenames and source format. This does not detect sensitive pixels: identity, payment, full serial and former-owner evidence must use the classified case route.

The authenticated composition supplies actor and selected business. Thread and watch must be resolved through the conversation provider, never accepted as authority from a browser. Every command binds actor, business, thread, watch, expected source revision, purpose and exact input digest to a stable operation. Upload and attachment use separate stable references. A conflicting duplicate returns `operation_conflict`; an identical retry returns its durable receipt after checking current access. Operation lookup has the same current scope checks. Unknown operations remain pending, never successful. Unavailable or lost responses retry the exact operation, without automatic retries. Stale writes require current conversation review; historic attachment versions do not convey authority.

The current-access provider must acquire a serialized lease within two seconds, covering the complete local read or transaction. Membership, identity, organization, record, watch, assignment and revision changes must serialize with this lease. Missing facts or a failed acquisition raise unavailable. There is no permissive default. Ordinary blocked members cannot read or write. A specifically assigned support participant may continue only while that same scoped active obligation remains; ordinary business or operator roles are insufficient.

Metadata, ordered paginated listings, version information, operation receipts and bytes are private. Responses use no-store, same-origin and no-referrer headers. No public or signed bearer URL is issued. Events contain a thread invalidation only, with no private evidence reference. No photo bytes or original metadata enter logs, previews or browser persistence. Attachment plus receipt plus outbox commit atomically. The source conversation revision stays with its producer; this module never changes that authority.

Unattached uploads expire at exactly seven days by authoritative UTC epoch seconds. Run the local sweep regularly; access also rejects an expired orphan even before sweep. Per-actor conversation storage is bounded to eight photos, including orphans. Listing limits are 1–50 and totals come from storage. Attached evidence retention and redaction require the current case/obligation lifecycle; deleting a public conversation screen does not authorize deleting protected records.

`fixtures.json` contains synthetic deterministic success, denied, stale, lost-response and unavailable states. They are development fixtures, not connected acceptance.

Results, durable receipts and unknown-operation lookups use the same stable envelope: `schema_version`, `operation_id`, `subject_id` (conversation), `watch_id`, `actor_id`, `organization_id`, `expected_revision`, `state`, `revision`, `pending_reason`, `next_actor` and `next_review_at`. Completed results have null recovery fields. Unknown results bind the requesting scope with `result_unknown` and the requesting actor as the next actor; no review appointment is invented. Request parameters retain the stable `operation` reference.
