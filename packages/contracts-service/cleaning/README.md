# External cleaning V1

This additive module owns a separate external case/bracelet request and an immutable accepted line. It cannot authorize opening, polishing, movement work, submersion safety, completion, charging or release. Process selection belongs to the current brand/dealer assessment. No appointment or private file upload is created here; restricted evidence remains with scoped intake.

Operations: `POST /v1/cleaning/requests/{subject_id}` accepts Command; `GET /v1/cleaning/requests/{subject_id}` returns `{record: Result|null, quote: Quote|null, binding}`; `GET /v1/cleaning/operations/{operation_id}?subject_id=…` recovers a lost response; `GET /v1/cleaning/requests/{subject_id}/readiness` returns current execution readiness. Every call requires current authenticated identity, buyer ownership, selected business, supported capability and record scope. Subject is the provider-owned service request identifier, never an arbitrary watch identifier. Commands bind actor, business, watch, source/policy and expected cleaning revision. Operation lookup requires the same current authority, even for duplicates. Same reference and same payload returns its retained result; another payload conflicts. Revision mismatch requires review, never silent replay with changed scope. Unknown results remain pending; retry the identical reference/body or look it up. Denied, stale, unavailable and operation conflict are distinct stable codes, translated by the view. No request or evidence contents enter events or logs.

The host supplies an authenticated principal dependency and a current-facts provider to `make_router`. This provider must serialize validation and consumption with source authority: its async context manager `current(principal, subject_id)` holds that authority through the local transaction. Calls have a two-second whole-operation budget; no background or automatic retries. Missing integrations fail unavailable. Facts include current assignment, capability, consent, quote, Orders job/payment, custody and canonical watch commitment. No local projection supplies these facts. Provider retention of accepted economics must be atomic with its serialized source operation; acceptance here records customer acceptance only, never silently commits a preview or creates an order. Current quote must be retained (`accepted_at` present, `expires_at` null) before execution. Execution readiness is informational and must be rechecked by the canonical job command under its own lock. No second allocation or financial journal exists here.

A quote binds the exact request revision, current assessed line, areas, condition and preservation limits; distinct assessor/approver, current assignments/capability, process, limitations, lead time and full terms are mandatory. No assumed submersion safety is allowed. The complete separate assessed line is explicitly accepted; changes require a new request assessment and quote. USD cents are strict bounded integers, customer total equals base, and the business fee is one half-up 5% fee, with no buyer surcharge. Equality at preview expiry denies acceptance; retained economics never expire as prices. Current source, consent or authority changes can still prevent execution without rewriting accepted history.

`fixtures.json` is synthetic contract data, never connected evidence. Connected S01/S02 provider, source serialization, retention, database migration/outbox delivery and canonical execution proofs remain owed. The host owns registration; this module does not edit shared runtime composition. Outbox records contain only scoped identifiers and revisions; host delivery must use the existing transactional relay/inbox contract.

Execution facts include the published Orders paid-readiness shape under `payment`, with the local servicing kind `service`; the real producer must confirm this discriminator before connection. Readiness checks exact buyer, order, watch, retained quote/revision, USD total and payment operation/revision. Current custody and canonical commitment each bind the same order/watch. Boolean readiness alone is insufficient. The view links to the localized inbox for support before acceptance and during uncertain-result recovery. Shared shell selection and page delivery registration remain required before the route can mount its shared reads.

The store receives the authoritative clock as a callable and samples it only after the subject, operation and record locks have been acquired. Acceptance at or after preview expiry is refused, including when expiry passes during a lock wait. A recorded identical retry returns its original receipt without applying a new deadline decision.
