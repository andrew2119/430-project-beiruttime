# Technical intake V1

`GET/POST /v1/intake/records`, `GET/PUT /v1/intake/records/{id}`. Select a business with `?organization_id=<uuid>`; Identity verifies this selection through `/internal/v1/principal?organization_id=<uuid>`, and a mismatched response is denied. Current selected organization, current membership and `business.records.read` / `business.jobs.write` organization grants are mandatory for reads/writes respectively. Explicit existing `intake.read` / `intake.write` grants are accepted as equivalent only inside the same verified selected organization. No operator override. Mutations require Idempotency-Key; PUT also requires integer If-Match. Serial, reference, movement, condition, accessories and symptoms are private and never included in event payloads.

Without an Orders custody receipt the state is **awaiting_intake**, never received. Diagnostic opening readiness also requires opening permission and both no-polish/fee acknowledgements. Detail reads freshly revalidate the Orders receipt: a historical `received` record remains readable, but a newer custody fact (409) or unavailable proof disables diagnostic readiness and returns `custody_verification: unconfirmed|unavailable`. No inspection, authentication, repair, payment or quality pass is implied by intake.

Provider seams:
- L11 `GET /v1/directory/providers/{organization_id}` returns `organization_id`, `official: true`, `active: true`, `kind: brand|dealer` for an onboarded business.
- L08 `GET /v1/custody/receipts/{receipt_id}` returns `id`, `order_id`, `organization_id`, `received_at` (aware UTC), `revision >= 1`, `valid: true`. A matching receipt alone admits received intake. Missing receipt endpoint is unavailable, not proof of custody. A record may be created awaiting intake without a receipt.
- Identity foundation CurrentPrincipal, with organization-scoped grants.

Private evidence uses `GET/POST /v1/intake/records/{id}/evidence` and `GET /v1/intake/evidence/{id}`, with the same selected-organization scope. POST requires Idempotency-Key and If-Match. Up to ten files per intake, each at most 262144 bytes. JPEG/PNG/WebP condition photos and those formats or PDF prior-owner records are signature-checked, stored only in the Service Operations database, and fetched through the foundation ScopedFiles adapter after authorization. Download returns authenticated JSON `content_base64` for an explicit client download; there is no public/inline preview URL. Upload increments the intake revision and appends an audit entry. File content, filenames and evidence never enter events.

Event `service-operations.intake.recorded.v1` has `record_id`, `order_id`, `organization_id`, `state`, `revision`, `custody_receipt_id`; producer `service-operations`. Transactional outbox destinations are Orders and Communications. Delivery uses RS256 `BT_INTAKE_SERVICE_PRIVATE_KEY`; missing credentials leave delivery pending.
