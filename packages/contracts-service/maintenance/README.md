# Maintenance requests v1

Submission records reported symptoms, known modifications, private photo references and limited assessment permission. It does not book an appointment, confirm receipt, establish a diagnosis or authorize execution. A destination must support the exact brand and intervention at the current capability revision.

The provider's `current` operation rechecks current identity, ownership, business and brand/intervention permission, exclusive watch commitment and each photo's owner, type, size and retained access. At most ten files of 256 KiB each are accepted. Metadata stripping and safe-photo declaration remain prerequisites; no pixel detection is claimed. Missing facts return pending; permission denial returns denied; changed revision returns stale. Dependencies have a 1.2-second budget. The transaction factory serializes operation admission, bounds lock waits and commits request, receipt and outbox together. Retry or lookup uses the original operation reference, actor and business. Conflicting reuse denies. Current authority is checked before replay.

The module leaves are additive. Shared runtime registration, provider integration, database rollback/restart and outbox delivery proof remain deferred to composition. A local fixture is never authority for payment, custody or execution.


The current-authority response has its own strict schema. It echoes actor, subject, operation, watch, organization, brand, intervention and current revisions; every permission flag must be a literal boolean. Context exposes only current eligible destinations. Private photo preparation rechecks watch/business access, validates bytes and declared type, strips metadata, bounds count/size and durably deduplicates its own operation before returning a reference. The injected identity resolver uses the current identity contract; no local credential interpretation is introduced. No provider is installed by default.

After current permission checks, an identical committed operation returns its durable receipt before comparing source revisions for new admission. A conflicting transport response is resolved through authenticated operation lookup; unavailable lookup preserves the original reference. Lookup resolves the original watch and intervention from the scoped retained request. Current admission authority must confirm the buyer still owns that watch before lookup returns the receipt. Changed revisions never turn an uncertain committed submission into a new request.

The service registers request submission, context, lookup, private photo and received-case diagnosis transport. Request-scoped adapters authenticate the current personal buyer, require current ownership/destination context, and verify every private photo reference against its actor, watch, business and request operation. Private images are decoded and re-encoded before durable storage; retries bind the original operation and bytes and each request admits at most ten references.

`POST /v1/service-cases/{case_id}/diagnosis` accepts the bounded `Diagnose` contract. The case ID is the actual received intake ID, distinct from the submitted maintenance request ID. The command binds both IDs, watch, business, actor, assignment revision, expected diagnosis revision, explicit diagnosis and assessed lines. On physical receipt, intake stores the request ID from the signed opening authority after matching the acknowledged submission and the current assessment-fee order commitment. The private intake receipt returns both identifiers. Diagnosis and acceptance resolve this link from Service Operations records. Current opening authority must confirm the exact custody receipt, current assignment, watch revision, opening consent, fee and no-polish acknowledgements. Admission and symptoms never create a diagnosis.

`GET /internal/v1/service-cases/{case_id}/diagnosis` is restricted to authenticated Pricing and Orders callers. It exports the retained assessment and case revisions, buyer/business/watch, USD diagnosis and exact assessed lines only after rechecking current opening and assigned-record authority. Pricing uses `case_id` as its source ID.

The connected assessment command is `POST /internal/v1/service-cases/{case_id}/diagnosis`. Its private acknowledgement reports `state: assessed` and retains `status: diagnosed` for the diagnosis source. `GET /internal/v1/service-cases/{case_id}/diagnosis/operations/{operation_id}` returns the same immutable acknowledgement to the original diagnostician with current assigned write access. An unknown or differently scoped operation returns 404. Command acknowledgements and operation lookup recover historical findings. Only the authenticated current read derives diagnostic permission after validating current opening authority.

Maintenance context, admission, opening authority and assignment require current private producer inputs through `maintenance_context`, `maintenance_admission`, `intake_opening_authority` and `intake_record_access`. Missing or incompatible inputs withhold the protected operation.

Admission also verifies the destination's current servicing capability through Identity. Service Operations verifies the current Orders opening authority and the diagnostician's separate write assignment. The signed opening response supplies the assigned custody projection, whose order, business, receipt ID, revision and received time must match the intake. A diagnostician needs current job write permission and the case assignment.


Diagnosis admission binds the assessment fee quote identifier and revision to the current Orders commitment. Current diagnosis and accepted scope reads recheck the retained fee quote against opening authority and the commitment. Earlier acknowledgements remain available through operation lookup. A diagnosis without a retained fee quote requires a new assessment operation before export.

Paid repair work verifies the immutable diagnosis acknowledgement and its assessment fee quote binding against the received intake. Once the paid repair order holds the watch reservation, work admission checks current custody and commitment for that paid order.

The current diagnosis read also verifies the immutable diagnosis acknowledgement and the original maintenance submission acknowledgement. A missing or mismatched acknowledgement withholds current diagnostic permission.

New submissions require the admission capability revision to match the live servicing business revision. A revision change leaves the original submission receipt recoverable under the existing operation reference and current permission checks.

The diagnosis acknowledgement retains the Orders incident revision. Current diagnosis and new repair-scope acceptance require the same revision from opening authority. A changed or missing incident revision requires a new diagnosis operation. Historical operation lookup preserves the original acknowledgement.

Pricing acquires the source fence with `POST /internal/v1/service-cases/{case_id}/diagnosis/authorization` and the `DiagnosisAuthorization` body. It supplies the original decision operation key, quote ID and revision, buyer and business, and expected case and assessment revisions. The private response is an open newline-delimited JSON stream. Its first line contains `authorization`, which echoes the exact decision binding, and `diagnosis`, which contains the locked current diagnosis and assessed lines. Pricing must validate both against the quote and keep the response open through commit or rollback. The source locks the diagnosis, intake, request link and matching acknowledgements until Pricing closes the response or the eight-second request deadline expires, whichever comes first. A competing fence on the same case returns 503. Pricing must treat interruption or unavailable authority as a failed fence and recover uncertain decisions through the original operation reference.
