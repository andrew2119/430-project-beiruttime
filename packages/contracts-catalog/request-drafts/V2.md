# Catalog requests v2 — frozen 2026-11-05

Source baseline `1016d21`, pre-window candidate on `bt/bt-s2-l15`. Additive to v1 private drafts. Canonical `/v2` service commands have identical additive `/v1` aliases where registered for the frozen public gateway; existing v1 draft endpoints are not reinterpreted. Technical corrections remain server-to-server only, not a browser capability. This is a shape freeze, not connected acceptance. Python `v2.py` is the command schema. All IDs are UUIDs; revisions are positive integers; money is integer minor units from Pricing, never from option totals. Unknown outcomes stay pending/unavailable.

`source.tar.gz` contains only Catalog-owned runtime/modules/contracts and the Catalog lane fixture suite, plus its own registration/fragment. Extract locally against the existing main module set and published foundation-extension/v2 for connected checks; never commit another lane's copied source. `source-files.json` records candidate hashes and the baseline commit; implementation commit provenance is populated once the permitted commit window opens. `request.v2.json` wraps one deterministic, explicitly sample request and minimal event data. Static fixture references are not authority in a real operation transcript.

## Operations

- `POST /v2/configurations/{configuration_id}/validate` body `{configuration_revision,movement_selection_id,movement_revision}`: current buyer-owned four-option configuration plus their same-brand movement selection. Returns `{status:valid|incompatible|parts_unavailable|manual_assessment,fields:{dimension:code},digest,snapshot}`. Snapshot `{brand_id,base_model,caliber,selections:{color,material,dial,sophistication,movement},reference_ids}`; each selection has `option_id,option_revision,definition`. No physical-feasibility or price acceptance is inferred.
- `POST /v2/request-drafts/{draft_id}/submit` body SubmitRequest, Idempotency-Key required: returns `{id:operation_id,status:succeeded,resource_id,request:{...}}`. Serializes draft revision and all five current option revisions; submitted source cannot mutate. Same command key replays same request; different body conflicts. Invalid/missing/stale selections leave draft unchanged with per-dimension errors.
- `GET /v2/customization-requests` and `GET /v2/customization-requests/{request_id}`: current buyer or scoped target-brand staff only. Request `{id,revision,buyer_id,brand_id,draft_id,status:submitted,configuration_digest,configuration,watch_context,watch_reference,scope_intent,notes,created_at}`. Notes/images are private and never enter events. Each revision is immutable; no request flag authorizes work/payment.
- `GET /internal/v2/customization-requests/{request_id}?expected_revision=N`: RS256 service token, aud catalog, producers service-operations/pricing/eligibility/orders only. Minimal current request DTO (id,draft_id,revision,buyer_id,brand_id,configuration_digest,configuration without reference_ids,watch_context,status,created_at); omit notes/evidence/contacts. Current mismatch 409. This is the L17/L14/L19/L21 consumer read seam.
- `POST /v2/customization-requests/{request_id}/corrections?organization_id={brand_id}` body Correction: server-to-server only. Send fresh human Bearer authorization plus `X-Service-Authorization: Bearer <RS256 service token>` (issuer Identity, aud catalog, type service, sub service-operations, required exp/iat). The target-brand human still needs current business.jobs.write scope. Service Operations must first durably fence its current qualified claim/assignment against reassignment and retain the same Catalog idempotency key before HTTP; it alone owns that authority, not a copied Catalog assignment model. Bare browser role/permission is insufficient, and the gateway deliberately does not expose this command. Same-brand/base/caliber current options only. Creates N+1 immutable revision, retains history, invalidates all old bindings. Buyer reviews/reaccepts subsequent quote; correction is not acceptance. Source movement mounting configuration is retained and revalidated. No correction while a decision intent is unresolved or the current scope is approved.
- `GET /v2/customization-requests/{request_id}/revisions`: private current-party immutable history with actor/reason; current request APIs always return the latest revision. Request lists accept an optional draft_id for exact source reopening, plus before/next_cursor pagination scoped to the current party; another party's cursor is rejected.
- `GET /v2/customization-requests/{request_id}/references/{reference_id}`: current buyer/target-brand scope and exact attached reference membership before bytes; no-store PNG, no public image optimizer. Unattached source inventory is never submitted.
- `GET /v2/customization-operations/{operation_id}`: current buyer or authorized target-brand staff. Stable outcome lookup for submission/correction; no anonymous lookup.

## Brand decision handoff

`POST /v2/customization-requests/{id}/decisions` body Decision: exact request/assessment/quote/grant IDs AND revisions; attributable reason, selected target brand; buyer and reviewer cannot approve their own case. Prepare intent durably before calling Eligibility; `GET /v2/brand-decision-operations/{operation_id}` reconciles, never optimistic success. Current decision read `GET /v2/customization-requests/{id}/decision` and service-only `GET /internal/v2/customization-requests/{id}/decision` return pending/approved/rejected/denied plus exact bindings, actor/reason. An approved record is NOT an execution grant. L21 must recheck Eligibility and current request/quote/payment/allocation at job start.

Read-only `/v2/customization-requests/{id}/decision-readiness` returns an explicit discriminated status. Only `{status:available,bindings,execution_authority:false}` carries exact ApprovalBindings. A bounded prerequisite outage returns HTTP 200 `{status:unavailable,code:approval_unavailable,execution_authority:false}` without bindings, so an optional upstream does not poison the healthy Catalog BFF circuit. Permission/stale/expired denials remain denials. Clients discard failed/in-flight rechecks; commands independently reauthorize and never treat a read as execution authority. See brand-decisions/v1.ts and its versioned brand-decisions/v2 publication.

Provider dependencies: Pricing follows published `pricing-current/v2`: service GET `/internal/v2/quotes/{quote_id}/validation?buyer_id=...`, strict brand/current accepted scope and exact minor units/policy. Readiness derives that quote ID from the scoped grant rather than a raw-reference form. The assessment adapter follows the common assessed-quote seam `/internal/v1/brand-assessments/{assessment_id}/current` until L17 publishes its own freeze; it requires exact request/organization/revision, current feasible status and explicit qualified=true; absent qualification is not a pass. Eligibility's provisional fixture seam is GET `/internal/v1/grants/requests/{request_id}?purpose=brand_approval`, POST `/internal/v1/grants/prepare` and `/consume`, stable operation_id plus exact request/quote/assessment/grant/buyer/brand/approver/amount/currency bindings. Confirmation requires an exact matching current serialized result; no detached eligible flag is accepted. These two provisional adapters must align with provider freezes before connected acceptance. Missing provider is unavailable, never a pass. Rejection requires the same current bound scope but does not consume execution authority.

## Errors, events and fixtures

401 unauthenticated, 403 wrong organization/permission or self approver, 404 private unknown, 409 stale revision/digest/idempotency conflict, 422 incomplete with `details.fields`, 503 bounded dependency unavailable. Stable operation identity survives lost responses. Events `catalog.customization.submitted.v2`, `catalog.customization.corrected.v2`, `catalog.brand-decision.confirmed.v1` expose only request_id/request_revision/brand_id, no private content. Receivers must be published/allowlisted before relay enablement; outbox intent still commits atomically.

Deterministic cases: complete current five-dimension configuration -> one immutable request; missing movement -> fields.movement=missing; old color revision -> fields.color=stale_option; another brand/base -> incompatible; no declared compatibility rule -> manual_assessment (not feasible); inactive part -> parts_unavailable. Replaying submit does not duplicate. Expired quote/revoked grant/self reviewer cannot approve. Lost grant response -> pending with same operation_id, not approved.
