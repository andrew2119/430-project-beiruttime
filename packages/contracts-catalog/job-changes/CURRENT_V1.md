# Material job changes v1

Private commands: POST /v1/jobs/{subject_id}/changes; GET /v1/job-change-operations/{operation_id}; POST /v1/job-change-operations/{operation_id}/resume; POST /v1/job-change-operations/{operation_id}/accept.

The command uses Change in v1.py. Acceptance uses Approval. Unknown fields are rejected at the HTTP boundary. The stable operation reference binds the entire immutable command, including actor, business, watch, source revision and retained economics. A conflicting replay returns conflict; an identical retry returns the retained result after current authorization. Lookup and every retry require current identity, business membership, assignment and record permission. Lists use at most 50 rows per page and authoritative totals. No public endpoint, evidence, attachment or log payload is supplied by this module.

The response envelope contains schema_version, operation_id, subject_id, watch_id, actor_id, organization_id, expected_revision, state, revision, pending_reason, next_actor, next_review_at. execution_authority is always false. Old scope and economics remain immutable. A local pending intent immediately blocks local continuation; only a durable exact Orders hold acknowledgement permits changing the scope pointer. A hold denial or missing response leaves the old scope paused locally and the amendment pending. No cache or local receipt authorizes work.

Providers must recheck authoritative current identity, business, assignment, watch commitment, consent and scope for each call, serialized with their own mutations. hold(change, timeout_seconds) acknowledges operation_id, order_id, subject_id, watch_id, actor_id, organization_id, expected_revision, source_scope_id, proposed_scope_id, retained_quote_id, retained_quote_revision, responsible_operator_id and state=held. resume(change, approval, timeout_seconds) returns those same bindings with state=reapproved and the exact approval object. Identical calls reconcile lost responses using the same operation reference. Calls are bounded to three seconds; no automatic unbounded retries.

current(change, approval_or_null, timeout_seconds) returns true only after authoritative source checks. With approval it additionally verifies actual current assessment, quote, independent eligibility and brand decision, explicit acceptance by the buyer, consent and exact Orders paid-held readiness. All identifiers and revisions must match Approval, and eligibility reviewer differs from buyer. The brand decision must be newer for the changed scope; old proof cannot pass. accepted_at must be no later than authoritative current UTC. Expiring grants are invalid at equality. Retained quote expires_at=null preserves economics only. Amount includes no buyer surcharge; the single business fee is five percent rounded half up. No provider operation collects or releases money here.

The additive module is not registered by this change. Runtime composition, transactional database adapter, actual C12/C14 and Orders providers, and HTTP identity adapters are connected finishing prerequisites. The local durable store exercises recovery and an atomic workflow outbox; it owns no allocation, balance or execution permission. Outbox delivery must be wired to an idempotent inbox by the runtime owner. Durable hold acknowledgement and a local pause cannot retract work already performed before this command reaches Orders.

The command actor is the buyer; business staff cannot accept for the buyer. The current provider confirms the named responsible_operator_id assignment, retained as next_actor on held states. First response is due after 24 hours; escalation_at is 48 hours after the original intent, and retry never restarts either instant. The runtime must schedule escalation for that named operator without changing custody or financial state.

GET /v1/jobs/{subject_id}/change-review returns ChangeReview in v1.ts, after current private permission. Its operation reference is stable for the current proposed revision; an existing intent returns its exact reference. scope and terms contain complete EN/AR text for the actual proposed changes, limitations, accepted lines, old/new USD amounts and warranty. approval is null until fresh independent decisions and exact held-payment readiness pass. It contains no private evidence. Changing language only selects presentation text; acceptance is an explicit command and the server stamps accepted_at. Browser locale clocks never establish acceptance time.

When pending acceptance prerequisites become stale, resume first calls reconcile(change, approval, operation_revision, timeout_seconds). Orders must serialize this with execution and durably fence that exact approval against all delayed deliveries. Only a terminal state=not_applied receipt with the exact hold bindings, approval and operation_revision allows a revision-incrementing return to awaiting_reapproval. Unknown, applied, conflicting or unavailable results remain pending; they never permit replacement acceptance. Fresh acceptance uses the same operation reference and new proof after this transition. Orders must retain fenced approval attempts separately from the stable operation reference. This provider operation is a connected finishing prerequisite; absence leaves the operation pending.
