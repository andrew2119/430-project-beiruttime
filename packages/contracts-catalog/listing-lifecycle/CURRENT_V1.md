# Private listing lifecycle v1

Opt-in module contract. No public evidence or customer payment data is returned.

`POST /v1/seller/listing-lifecycle/commands` accepts the immutable Command in v1.py and v1.ts. `GET /v1/seller/listing-lifecycle/operations/{operation_id}` returns its current Receipt after current identity, organization and record authorization. Unknown references return not found within the authorized scope. Reads are private, no-store. An operation reference cannot be reused with different input. Revision conflicts require a fresh read and explicit new request. Transport failure requires lookup or retry of the same reference.

The runtime steward supplies current authorization and a canonical serialized lifecycle transition. That transition must atomically fence the physical watch across sale and job routes, check auction bids/reservations/winner/payment/custody, and persist an idempotent result keyed by the full command. A cache or preliminary availability read cannot substitute for this transition. The module never allocates stock, charges money or changes an old winner.

Pause stops new sales only when no commitment exists. Renew and relist require unsold or withdrawn source stock, current facts and terms, fresh listing-scoped reviewed possession, and a new linked auction identity for auction stock. Relisting creates a new listing identity for the same physical watch. Sold, unknown-payment, held-payment, reserved and bid-bearing stock deny every action. Unconfirmed renewal remains inactive. Existing transaction and contact duties are retained.

Possession verification consumes a new single-use code and private photo submitted strictly before issued_at + 24 hours, with issued_at <= submitted_at <= reviewed_at <= server now, current watch/source revision and assignment. Each lifecycle operation consumes a fresh proof. Proof references never appear in events, public fixtures, logs or previews. Accepted economics are references only; the pricing producer validates current USD integer-cent economics and explicit accepted terms. No preview extends past fifteen minutes; retained amounts confer no execution permission.

The injected transition has a two-second call budget, no automatic fresh-reference retries. Its response binds the exact command, authoritative revision, new identifiers and previous auction. Definitive denial is retained; missing, malformed or uncertain responses stay pending. Final local receipt and private outbox entry commit together. The outbox contains only operation, subject and result revision. Recovery reuses the same upstream reference after restart. Current authority is rechecked before returning any result.

This module is additive and is not registered in shared runtime files. Connected identity, possession, pricing, auction and exclusive-watch transition integration is owed before acceptance. Local durable storage is a focused adapter, not another stock or financial authority. Runtime composition must provide a durable database implementation with the same transaction semantics and an inbox for provider notifications.

All three actions require fresh reviewed possession. The deterministic fixtures are synthetic protocol examples only; they are not evidence of accepted proof or provider execution. `command.schema.json` rejects unknown fields and bounds references. The production route must bind actor and organization from the authenticated principal rather than trust submitted identifiers, enforce a small JSON body limit, and map internal reason codes to complete EN/AR recovery copy.

Pending receipts durably bind `responsible_operator_id` (one assigned support operator), `next_actor: "support"`, `next_action: "resolve_confirmation"`, `next_review_at` (authoritative UTC creation time plus 24 hours) and `escalate_at` (creation time plus 48 hours without progress). Runtime composition must supply the assigned operator before preparing any request. These fields commit with the initial pending receipt before the provider call. Lookup, timeout, malformed answers, retries and restart retain the original assignment and deadlines; retries never reset either clock. Terminal receipts clear these support fields. The scheduler connection remains owed: it must dispatch the first response by the review deadline and escalate at the escalation deadline when no progress is recorded. At equality each deadline is due. Seller recovery checks the same operation while support resolves confirmation.
