# Configuration validation v1

Additive all-five Catalog composition, using original four option and movement source contracts unchanged. See request-drafts/V2.md for validation and submission bindings. `v1.py` freezes Validate and Rule commands. Canonical `/v2` paths have identical `/v1` browser aliases.

GET `/v2/brands/{brand_id}/compatibility` lists current bounded rules. PUT `/v2/brands/{brand_id}/compatibility/{rule_id}` requires the current selected onboarded brand's business.jobs.write permission, expected_revision, base_model, caliber, exactly five distinct current brand option IDs with an exact option_revisions map, actual movement mounting `{case,dial,hands,functions}`, explicit status and reason. Revisions are additive; a rule never mutates an accepted request or quote. Repeating the same rule ID/expected revision, actor and normalized payload recovers its immutable acknowledgement without another version/event, even after a later rule revision. A different payload/actor is stale. This acknowledgement does not reactivate an old verdict or claim that old source options are still current. It validates each source's base/caliber and supported fittings, and does not publish a second service menu or price calculation.

POST `/v2/configurations/{id}/validate` accepts Validate. Personal buyer ownership/current source revisions are mandatory. Missing/stale choices produce precise field errors. Validation distinguishes `valid`, `incompatible`, `parts_unavailable` and `manual_assessment`; no current matching brand rule defaults to manual assessment, not valid. A rule binds actual fittings and all five option IDs/revisions, so a different mounting or revised option does not inherit another configuration's declaration. Publishing from an old snapshot denies rather than silently signing off changed definitions. Every result keeps `physical_feasibility_pass:false` and `price_acceptance:false`.

The immutable snapshot includes only explicitly attached owner-private dial references, not uploaded inventory. All reads and the submit command share the existing movement-selection, brand-catalog and configuration locks. No source module or legacy option contract is reassigned or rewritten. Deterministic boundary fixture descriptions are in fixtures/boundaries.json; full PostgreSQL command/race/privacy proofs are in the lane suite.
