# Brand decisions and read-only readiness

Commands and immutable request scope are in request-drafts/V2.md. Closed reference-only events remain v1 (`v1.py`). `v1.ts` defines exact ApprovalBindings and the discriminated DecisionReadiness response; the versioned publication is brand-decisions/v2. A retained approval is not payment, an execution grant or a job.

GET `/v2/customization-requests/{id}/decision-readiness` (additive browser v1 alias) first checks fresh actor/target-brand/current request permission. Available reads return `{status:available,bindings:ApprovalBindings,execution_authority:false}`. A bounded prerequisite-service outage returns HTTP 200 `{status:unavailable,code:approval_unavailable,execution_authority:false}` with **no bindings**. This optional read must not open a healthy Catalog circuit and prevent unrelated listing/request reads. Wrong permissions still deny; expired/stale/mismatched facts do not become available.

Clients must branch on status, discard failed/in-flight rechecks and never treat a truthy unavailable object as authority. Decision POST remains a separate current-scope guard: it persists intent before HTTP, returns unavailable/pending on uncertain authority results, and confirms only after exact serialized acknowledgement. No read creates a decision, consumes a grant, authorizes work or copies private eligibility evidence into Catalog.

Current source contract is `current.py` (`brand-decisions.current.v3`). Its operation lookup and deterministic success, denied, stale and lost-response fixtures are development inputs only. Quote validation uses Pricing v3. Accepted unchanged USD economics survive review without a price clock; grant expiry remains exclusive, so equality denies. Missing assignment, independent assessor, active consent or serialized grant acknowledgement fails closed. The assessment source must supply `assessor_id`, `approver_id`, positive `assignment_revision` and `approval_assignment_current:true`; the grant source supplies positive `consent_revision`, `consent_status:active` and no `revoked_at`. These fields are checked at preparation and retained in the exact consume binding. Eligibility must serialize current consent, assignment and revocation against that binding; a cached projection cannot authorize confirmation.

Pending intent is durable before any remote call. An uncertain response preserves that operation; lookup and resume use its stable identifier. Duplicate commands retain the same operation and conflicting payloads deny. No payment readiness, capacity evidence or collected payment is a decision prerequisite. Approval never authorizes execution. Connected assessment, grant and Pricing v3 acceptance remains required before feature acceptance.

`CurrentOperation` exposes the stable envelope alongside the existing response fields. Subject, watch and responsible operator are retained before any remote call, with a 24-hour response deadline and 48-hour escalation deadline. Lookup and resume preserve these deadlines across restart and retries. At equality a deadline is due; overdue pending operations request response or escalation without becoming confirmed. Terminal responses clear next-action fields. Missing current watch or operator assignment returns unavailable; existing terminal results remain readable without recovery metadata, with unknown historic subject/watch values represented as null. Existing pending results expose `restore_recovery` and the current assigned operator. The current request provider must supply `watch_id` and `recovery_operator_id`; connected assignment proof remains deferred.


Recovery actions `restore_recovery`, `reconcile_operation`, `respond_to_operation` and `escalate_operation` use POST `/v2/brand-decision-operations/{operation_id}/recovery`. This endpoint requires fresh business permission, private record access and the current recovery assignment. It records durable response/escalation timestamps and restores missing metadata under the request revision guard, without contacting grant authority, changing the original decision actor or confirming a decision. Existing creation time controls restored deadlines; unknown creation time makes follow-up immediately due. Repeated follow-up preserves deadlines and first acknowledgement times. These are coordination actions; only the original authorized decision actor can use `/resume` to reconcile serialized approval. A reassigned operator must use the current assignment, regardless of a retained previous operator identifier. Missing current assignment remains unavailable and requires assignment restoration by the assignment provider.

Current bindings include the canonical request `watch_id`, also supplied by the grant. Both prepare and consume acknowledgements must echo that exact binding. Retained pending bindings without current USD, consent revision, assignment revision or matching watch scope remain pending and unavailable for reconciliation; they are never upgraded or sent for consumption. Historic terminal bindings remain readable. The same operation reference is preserved for recorded reconciliation.
