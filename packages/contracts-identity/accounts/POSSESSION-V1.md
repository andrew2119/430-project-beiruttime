# Listing possession v1

All routes are private, no-store and require current identity and current listing ownership. Person-level seller approval never establishes possession. No challenge response, code or evidence enters public events or logs.

| Operation | HTTP path under `/v1/private-seller` | Result |
| --- | --- | --- |
| Current proof | GET `/listings/{listing_id}/possession` | `{proof: envelope or null}` |
| Issue | POST `/listings/{listing_id}/possession/challenges` | `{proof: envelope}` |
| Submit | POST `/listings/{listing_id}/possession/submissions` | `{proof: envelope}` |

Commands require an 8–100 character Idempotency-Key and expected_revision. Submit also requires challenge_id, code and photo_base64 (a synthetic PNG, at most 1 MiB decoded). Arabic digit forms are accepted. A private photo must show the watch and code. The declaration is not pixel detection or authentication. Metadata is removed before storage. Issue expires at server issue time plus 24 hours; equality is expired. Submission consumes the code once and only creates pending assigned review. Review decisions remain with the independent review domain.

Receipts bind operation, actor, listing, watch identity/revisions and immutable request digest. Same-operation retry returns the original receipt after current permission and binding checks. A changed body conflicts. A changed watch or listing revision returns stale_proof and requires a new challenge. No uncertain response establishes success; retry the exact operation. Reissuing invalidates an unsubmitted challenge, never overwrites pending review. Relisting must advance listing_revision even for the same watch. GET reports expired/stale without claiming approval.

The injected `listing_possession_authority.current(actor_id, listing_id)` operation must return `subject_id, watch_id, watch_revision, listing_revision, organization_id, seller_status`. It must serialize current reads with listing mutations for a command's transaction scope; revision checks at publication remain mandatory. Only an approved personal seller with organization_id null may command. Calls are bounded to two seconds; absent/timeout authority returns unavailable, never a fixture success. This provider is a prerequisite for connected acceptance. Assignment, evidence retention/removal and review consumption require connected integration; these routes do not grant publication.

Deterministic fixtures cover issued, pending, denied, stale and lost response. Evidence references/bytes are deliberately absent from all envelopes and fixtures. Private storage must be included in the retention process: remove unsubmitted files after seven days, final-review evidence after thirty days unless held by an active case, and minimal audit references after one year.

The additive `L19.account-access` module registers `migrations/L19_0003_listing_possession.sql` and declares migration dependencies on `L01.accounts` and `L01.private-seller`. Runtime composition must admit L19 modules and honor their migration dependencies; the current loader admits only the original prefixes. The gateway must allow the three operations above with a bounded 1.5 MiB command body and no-store responses. Until migration and authority composition are present, proof operations remain unavailable. `sellerApplicationRead` defines the open-only question and cancellation. The mounted seller page uses `usePageRead` for retained answers and refresh, with `AnswerArrival` for the first answer. Its owned route declaration awaits shared shell adoption; connected navigation and measured first-frame proof remain owed.

The authority may include a current `review` from the independent review producer: `{challenge_id, proof_revision, watch_revision, listing_revision, verdict, reviewer_id, assignment_revision, review_revision, reason}`. Verdict is approved, correction, rejected or suspended. All bindings must match the submitted challenge, the reviewer must differ from the seller, revisions must be positive and the reason nonempty. A supplied mismatched or malformed review fails unavailable. Absence remains pending, never inferred approval. Correction/rejection allows a fresh code; pending/approved/suspended proof cannot be overwritten for unchanged listing identity. Review reason is private, remains as written, and is not publication authority. Producer assignment revocation and review freshness must be rechecked on every current read.

Owned photo removal is provided by `retention.reconcile_photo` inside a transaction serialized with current independent review and case-hold authority. Its private facts bind photo, listing, seller and historical challenge, final review time, independent reviewer, current assignment revision and an explicit active-case boolean. Missing or mismatched facts deny removal. It updates the review timestamp and hold, removes bytes at thirty days after final review when no active case exists, and removes overdue bytes atomically when a hold is released. Repetition after removal is harmless. Facts must cover historical challenges after relisting. External scheduling, producer serialization and connected retention execution remain owed. No unsubmitted photo bytes are stored by these routes; selected files remain only in memory.
