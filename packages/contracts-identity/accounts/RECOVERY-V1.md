# Recovery message language

`POST /v1/accounts/recovery` accepts `{email, locale?: "en"|"ar"}`. Omitted language remains English for existing callers. The public result remains the same generic simulated-delivery acknowledgement for eligible and ineligible recipients. Links last twenty minutes, are single use, and successful reset requires fresh sign-in.

The encrypted private recovery capture retains the request language and exact token. The permission-scoped recovery-message operation returns the matching `/en/account?mode=reset#…` or `/ar/account?mode=reset#…` link. Existing encrypted token-only messages retain English links. Tokens never enter query parameters, public responses or browser storage. Language changes preserve the mounted form and the exact pending request body/reference; they do not request a new recovery message.

Recovery requires an 8–100 character Idempotency-Key. A transaction-scoped operation lock serializes retries. A receipt binds the exact request digest, including language, for eligible, ineligible and suppressed recipients alike. Identical retries return the same generic acknowledgement without replacing a token or emitting another message; changed bodies conflict. The receipt, reset token, encrypted message and event commit atomically. Expiry or consumption never causes a retry to issue another token. A new request needs a new reference.

The additive `L19.account-access` module registers `migrations/L19_0001_recovery_receipts.sql` with migration dependencies on `L01.accounts` and `L01.private-seller`. Runtime composition must admit L19 modules and honor those dependencies. Until then recovery fails unavailable before changing any token. Connected migration and concurrent database proof remain deferred.

Reset and password change require an 8–100 character Idempotency-Key. The `L19.account-access` module also registers `migrations/L19_0002_password_receipts.sql`; absent storage fails unavailable. Each transaction locks the operation and commits its subject-bound receipt with the password, revocations and event. Reset receipts bind the exact token/password body. Password-change receipts additionally bind the exact original authorization header; first execution requires current identity and current-password proof. An exact replay returns only `{sign_in_required:true}`, even after token consumption, session revocation or credential expiry; it grants no session or mutation authority. Changed body or authorization conflicts. Receipt digests are keyed, with no plaintext passwords or tokens stored. Connected database concurrency and gateway replay remain deferred.

Unresolved form operations remain in memory across mode and language changes. An explicit retry sends the original endpoint, body, authorization and reference. Other form submissions wait for that result. No private body is persisted in browser storage.

Password receipt recovery uses the existing public `POST /v1/accounts/reset` admission with `{action:"password_receipt",current_password,new_password,authorization}` and the original Idempotency-Key. Authorization is the exact original header value carried privately in the body; omit the HTTP authorization header so an expired or revoked session cannot prevent receipt lookup. This branch only checks the keyed immutable receipt and never changes credentials or grants access. Missing receipt returns `operation_pending`; changed bindings conflict. Both remain unresolved in the form. First attempts refresh the session before binding the immutable password request; retries preserve that binding. Recovery retries first send the original command, then look up its receipt if the command response fails.
