# Identity Accounts v1

`GET /internal/v1/principal` accepts a Bearer RS256 access token, verifies its live account and unrevoked session lineage, and returns foundation `CurrentPrincipal`. Optional `organization_id` selects a currently held business membership. No caller actor header is trusted. Public user tokens carry subject/session only, never authority.

Account endpoints: `POST /v1/accounts/{register,login,refresh,logout,recovery,reset,password}`; `GET /v1/accounts/me`. Registration requires an Idempotency-Key (8–100 characters), email, password (12–128 characters), display_name. Login/registration/refresh return access_token (300 seconds), account, principal, access_fingerprint; a Strict HttpOnly bt_refresh cookie rotates at refresh. Logout, password changes, reset, suspension and token replay fence the entire session lineage. Explicit web origin is required for ambient-cookie/anonymous commands. Configure the comma-separated exact allowlist with `BT_ALLOWED_WEB_ORIGINS`, for example `http://localhost:3000,http://localhost:3101,http://localhost:3077`. Empty/unset falls back to `BT_WEB_ORIGIN` (default `http://localhost:3000`); wildcards, credentials, paths, query strings and fragments are rejected. `BT_WEB_ORIGIN` is also the canonical simulated-mail link origin. The lane fragment passes both variables to Identity; recreate the Identity container after changing local configuration. Browsers must still use the same-origin gateway, which validates and forwards Origin. Set the frontend's `BT_PUBLIC_WEB_ORIGINS` to the exact origins it publishes (including a Docker-published port when applicable); it must agree with Identity's allowlist. Keep `BT_TRUST_FORWARDED_ORIGIN=false` unless a trusted edge overwrites both forwarded host/protocol headers and prevents direct origin access. Never disable the check or add a wildcard. Recovery is generic; mail delivery is an explicitly simulated encrypted capture, never a public token response. `GET /internal/v1/accounts/demo-mail` returns at most 20 still-live captured recovery links only to a current principal with the explicit platform permission `identity.demo-mail.read`; no public gateway registration exposes this endpoint. Capture reads are audited and never log response bodies.

## Same-service extension seams

Identity modules can import `live_actor` from `service_app.identity`. Call it inside the owning unit of work; `lock=True` takes the account row lock shared by session mutation/revocation and returns `(account_row, session_id)` only for a current active account/session.

The Accounts module owns `identity_accounts(id uuid,email,display_name,password_hash,status active|suspended,access_revision)` and `identity_access_grants(id uuid,subject_id uuid,organization_id uuid nullable,role text,permissions text[],revoked_at)`. L02 may write grants in its authorized Identity transaction, increment account access_revision, and revoke `identity_sessions` for permission changes. Null organization means individual/platform authority. Non-null organization grants never become platform permissions. Do not expose password hashes or session token rows. No public operation grants operator, brand or dealer.

Private-seller module owns `identity_private_applications` and `identity_private_evidence`. The application has id, subject_id, revision, status (pending|correction|approved|rejected|suspended), identity_name, contact, payout_reference, reason, created_at, updated_at. L02 review may update this same-domain record under the applicant account lock and expected revision, and grant/revoke private_seller with identity.listings.publish in identity_access_grants. Evidence fields: id, application_id, subject_id, kind (identity|possession), content bytea, sha256, created_at. Reviewers must be assigned in `identity_private_assignments(application_id,reviewer_id,revoked_at)` and possess `identity.private-seller.review`. Reads of evidence are owner-or-assigned-reviewer only and audited. Cases are private; account API never leaks evidence. Approved seller identity is not a physical watch inspection.

All cross-domain consumers use HTTP and versioned events. Events contain opaque identifiers only and enter the durable foundation outbox; unavailable destinations leave delivery pending.
