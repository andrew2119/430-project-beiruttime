# Eligibility privilege administration

POST `/v1/memberships/eligibility-privileges` accepts the accompanying schema. A current individual `identity.membership.manage` permission is required. The recipient must be a different active account. The initial operator can use this operation to delegate individual `eligibility.identity.assign` authority to a separate account. Assignment and review permissions are individual. Prepare, consume and revoke permissions require an explicit active business and current membership. Qualification strings grant no permissions.

The operation identifier is immutable. An identical retry by a current administrator returns the same grant reference even after the recipient loses access; it leaves current permissions as they are. A changed payload or administrator conflicts. The reason must contain 10–500 characters after trimming surrounding whitespace. The reason and administrator are recorded durably with the security audit entry. Revocation removes the named permission from all active grants in its exact scope, including grants that bundle it with other permissions. Membership changes revoke these explicit business privileges, requiring fresh administration; business suspension revokes organization grants. This operation never grants case assignment. The case-owning service must independently authorize and record that assignment.

The same operation can grant or revoke individual `identity.private-seller.review` for a separate active account. It records a `private-seller.review.privilege` security audit entry. Reviewing a possession photo also requires current assignment to that photo generation.

A membership administrator can grant or revoke individual `identity.data-requests.restore` for a separate active account. This grant is audited under `data-request.restore.privilege`. The producer byte read also checks the operation, its current subject and scope, and the source retention decision.

A membership administrator can delegate individual `identity.data-requests.oversight` to a separate active account through the privilege administration route. The grant permits request oversight, including dispatch recovery and restore assignment for requests assigned to that account. Export creation requires an eligible operator distinct from the requester. If none is available, creation returns unavailable and the same operation reference can be retried once oversight is available.

Consumers of business permissions select the original business with the `organization_id` query parameter on GET `/internal/v1/principal`. For prepare, consume and revoke, use the business recorded on the consent and check the returned organization grant for the exact permission. Individual case reviewers use the principal's individual permissions and still require a current case assignment from the case-owning service.
