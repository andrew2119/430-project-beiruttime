# External sign-in v1

Private operations: POST `/v1/external-sign-in/challenges`, POST `/v1/external-sign-in/callback`, GET `/v1/external-sign-in/operations/{operation_id}`. These are additive composition contracts; no shared router registration is changed here. The callback accepts `Callback` in `current.py`; the current-operation response is identical to `index.ts`. GET requires the original browser binding and current actor/scope. Responses use no-store and no-referrer. Codes, state, nonce, recipient, external subject and link proof never enter URLs, previews, events or logs. The browser binding is a random Secure, HttpOnly, SameSite cookie supplied by the composition boundary; it is never accepted from JSON.

A challenge binds one stable operation, browser, actor, organization, current identity revision, issuer, audience and nonce. It expires after 600 server seconds; equality is expired. Five invalid callbacks close it. Creation is limited to five per browser per hour; the ingress must additionally limit network origins and request bytes. State and nonce use independently labelled keyed derivations from the random private browser binding and operation reference. An identical scoped challenge retry recovers the same values and original expiry, including after restart, without a new admission; a consumed operation returns a non-success state requiring authoritative lookup before any success can be shown. Only hashes of browser, state and nonce are retained. The return destination is fixed to `/account`; arbitrary redirect destinations are not accepted.

The provider boundary validates signature with a configured key and pinned algorithm, exact issuer and audience, nonce, subject, strictly verified recipient, issuance time and expiry. A profile, email match or business label grants no role, seller approval or business membership. The deterministic adapter is local synthetic data only and is never registered as a live provider.

The identity boundary owns current accounts, exact recipient ownership, business membership, account revision, fresh proof and sessions. `complete` must serialize with account/contact/membership changes and atomically link the unique `(issuer, external_subject)` plus the recipient to the current account and create a session receipt. For linking it consumes fresh proof of the current account bound to the exact issuer, external subject, recipient, actor, browser and operation. External proof supplies the other side. A collision without both proofs denies with ordinary sign-in/recovery available. New identities receive buyer access only. Business unavailability is pending; no role is inferred. Ordinary password sign-in and recovery do not depend on this module.

`complete` and `current` recheck current authority on every call. `complete` is idempotent by operation and the complete immutable binding; conflicting retries deny. A lost response remains pending and is retried with the identical operation. A current receipt never restores a revoked session. The public operation returns neither a credential nor recipient; the identity composition boundary delivers its own cookie without exposing it here. No sign-in is claimed until that boundary durably acknowledges completion. Link and sign-in receipts persist across restart; no second session or link on retry.

The local transactional store owns challenge admission and operation receipts only. Identity/session/link persistence remains with the existing identity owner. All calls have a two-second deadline. The identity implementation must honor cancellation or return a stable receipt after an uncertain commit. This module has no cross-service database imports, balances or grants. Private rows require service-only access and expiry cleanup under the identity retention policy. Database deployment, actual identity composition, cookie delivery, ingress limits and provider round trip remain connected acceptance requirements.
