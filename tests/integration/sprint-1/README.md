# Sprint 1 core-loop evidence

The evidence runner uses real same-origin gateway HTTP only. It never seeds outcomes, writes SQL, repairs data, drives service lifecycle, or substitutes a mock provider. An incomplete run is explicitly `complete: false` and lists unverified capabilities. A unit-test result is not full-slice acceptance.

## Run after the domain branches are integrated

1. Start the integrated foundation Compose application. Import **labeled sample content** with each domain's authorized fixture entry point. Use real private-seller review and operator-onboarded official businesses; never seed a winning bid, payment, watch authentication pass, completed job, receipt or payout.
2. Record fixture resource references and the supplier API steps in a local scenario JSON (inside this directory, ignored if it contains local-only values). Each step has `id`, `capability`, gateway `path`, optional `method`, `body`, `actor`, `operation_key`, expected HTTP `status`, contract `assert` list, and response `capture`. `${fixtures.watch}` and `${captureName}` interpolate references. Do not put passwords/tokens in the scenario.
3. Supply `BT_SPRINT1_CREDENTIALS` as a JSON object of actor aliases to real login credentials in the process environment. The runner logs in through Identity; no self-assigned role/actor header is accepted. Do not put this variable in shell history, commits or evidence.
4. `python tests/integration/sprint-1/runner.py <scenario.json> --origin http://127.0.0.1:3000 --evidence tests/integration/sprint-1/evidence/local.json` (Python 3.11 + HTTPX).
5. A racing step contains two `race` command specifications for the exact Orders reservation endpoint, different current principals and operation keys, and the **same** immutable physical-watch id. It requires exactly one succeeded awaiting-payment reservation and one `watch_unavailable` denial, both without payment authority. Ordinary steps require nonempty contract assertions, the owning service and an acknowledged HTTP status. Mutation capabilities require an actual mutation method and stable operation key; bid, maximum and draft acceptance additionally requires an explicit `status:succeeded` assertion. Health/status probes cannot satisfy coverage. Assertions support type-exact JSON match, inequality, containment, count, bounds, presence, false, strict bounded `integer` and aware `utc` instants. An expected unavailable source must actually return an upstream-unavailable status or an asserted unavailable section, never an unrelated successful read. Optional `upload` names a bounded attributed demo image under `web/public/demo/watches/` with a multipart field and content type. Captures/response bodies remain in memory; evidence contains only capability/status/time/request reference and safe failure codes. Authentication failure produces an incomplete redacted report. An expired actor may reauthenticate once using that same actor's in-memory credential and retry with the unchanged command key; a shared cookie jar never refreshes another actor's identity.
6. Verify the first-sprint browser matrix with `chrome-devtools-axi` in a named isolated session: checkout and resumed private draft at desktop and 390px; English and Arabic; light and dark. Confirm no horizontal overflow, no hydration errors, keyboard reachable controls, truthful dependency failure, cross-account denial, and locale-preserved same-profile neutral intent. Stop that named browser session afterward.

## Connected walkthrough: listing possession before publication

Use one owner-only proof run directory (mode `0700`) for the walkthrough and every resumed attempt. Run `connected_walkthrough.py publication --run-dir <run-dir>` with the same backend/origin as onboarding. The guarded Catalog import creates the exact demo draft, uploads its public illustrative image and requests publication; on an initial listing-review hold the command fails rather than claiming publication. Confirm the owning Identity listing-review record is awaiting the seller before taking any review action; do not treat every 503 as a review hold.

For the private demo reference currently blocked (the fixture order is `DEMO-WATCH-01`, `-03`, `-05`, interleaved with dealer listings), run `connected_walkthrough.py listing-review --run-dir <run-dir> --listing-reference <reference> --review-action <action>` with the same backend/origin. Use the following actions in order:

1. `challenge --review-file <new-private-code.json>`: the seller requests the owning Identity challenge for the bound draft. The walkthrough writes the one-time code to a new owner-only file in the run directory, never to the terminal. The seller supplies an actual private watch PNG (up to 750 KiB to fit the gateway's base64 envelope) for that challenge within 24 hours; do not reuse the illustrative catalog image or generate fake evidence.
2. `submit --review-file <seller-possession.png>`: send the seller-supplied owner-only PNG and exact challenge using the seller's own session. The raw image is not copied into the call journal.
3. `assign`: the authorized operator assigns an independent, currently qualified reviewer. The existing first operator holds both assignment and review permissions and is independent of the seller. To use a different qualified reviewer with gateway access, pass `--reviewer-credentials <owner-only.json>` containing their existing Identity login `email` and `password` for this and both following actions. No role is granted by the walkthrough.
4. `inspect --review-file <new-reviewer-copy.png>`: the assigned reviewer fetches the private image from Identity. The walkthrough checks it is the exact submitted byte sequence and writes a new owner-only copy to inspect. The reviewer opens that copy privately and decides the case; a byte match is not a reason to auto-approve.
5. `decide --review-file <owner-only-verdict.json>`: the reviewer supplies their actual `verdict` and `reason` after inspection. An approval is not implied; correction or rejection keeps publication incomplete. The request uses the exact active proof and assignment revisions.

Rerun the unchanged guarded `publication` command on the same state after an approval. It reuses the demo draft and original publish key, rereads the exact revision and stops if the next private draft needs review. Do not replace a draft or count a preapproved record. Final publication evidence requires the same reviewed listing/watch and the next publication revision for every private demo reference. If Identity really holds a matching stock digest, resolve that separate case with an authorized reviewer through the owning stock-decision route; the walkthrough never preemptively clears a duplicate. Stop on uncertain or changed binding, and keep code/photo/decision input files only within private evidence handling.

## Required capabilities

Private and dealer publication with photos; combined browse/search/detail; manual bid; confidential private maximum; canonical live projection/reconnect; exclusive Buy Now; scoped seller moderation; official service directory; supported business options; actual technical intake; private consent; buyer/seller/purchase/operator workspaces; persisted private draft; unavailable source; denied second seller; unreleased payment/closing/inspection/work actions denied.

`Runner.REQUIRED` is the machine-checked coverage set. It does not declare any capability verified merely because a route exists. Real supplier fixture entry points and final connected browser evidence must be recorded after integration; consumer HTTP fixtures are confined to `tests/lanes/L08/`.
