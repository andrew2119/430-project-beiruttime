# Native lane selection v1

Planning rejects missing test roots and required proof paths. Each required proof must contain static test definitions covered by the selection's test inventory. Collection validation independently requires cases under every declared required proof path, even when a supplied static inventory omits that proof.

The manifest preserves L00–L11 service selections, the separate L09 Directory/Intake integration selection, and required lifecycle coverage. Offline planning imports no suite and starts no process. Shared checks run once, including one web build. L05 notices retain their own module tree, the separate Auction tree, factory and helper imports, and the two-domain delivery test. L08 roots remain separate; L10 uses all four option roots with an empty core baseline.

`python3 scripts/native-lanes.py --all --plan` emits versioned requests and source/dependency fingerprints. Test identities are canonical repository-relative identities. Static definitions are a minimum inventory; parameter expansion, dynamic collection, and opt-in lifecycle activation belong to the collection provider. They are not proven by the offline plan.

Execution requires a new external run directory and explicit `--layout-provider` and `--collection-provider` files. The command invokes each supplied file with the current interpreter and `--request FILE --result FILE`. These v1 interfaces are proposed integration boundaries for N08 and N02, with N03 providing lifecycle coverage; connected compatibility remains deferred. The command grants no execution admission. Missing providers return nonzero. `--require-all` states the default strict policy explicitly.

The layout request is one selection from the plan, including schema version and request fingerprint. Its response contains `schema_version: 1`, the same `request_fingerprint`, `read_only: true`, and provider-owned layout data. The provider must preserve the declared roots, import order, path aliases, empty baseline and isolated database domains without modifying source or starting ordinary services. Source command paths are logical repository paths; the layout provider translates them to its read-only layout. Required dependency-pin and lint checks apply to the selected layout. Path aliases are compatibility requirements for existing tests, not permission to rewrite their files.

The collection request contains `schema_version: 1`, `selection`, and `layout`. Its response contains:

- `schema_version: 1`, `selection_id`, and matching request/source/dependency fingerprints.
- The exact requested `topology` and `result: "passed"`.
- `counts` with nonnegative integer `collected`, `passed`, `failed`, `errors`, and `skipped` totals.
- `collected_nodeids`, the exact collection inventory before execution, including every parameter case, and `nodes`, one `{nodeid, outcome}` per collected case. Outcomes use the count names except `collected`. Collection and execution identities must match exactly and cover every static definition.
- `skips`, one `{nodeid, reason, required}` per skipped case. No optional skip is currently authorized; a missing database or opt-in lifecycle case fails completion.
- `checks`, mapping every requested selection check to `"passed"`.

The final shared request contains `schema_version`, all shared `checks`, and the plan `request_fingerprint`. Its response binds that fingerprint and returns the exact check/result mapping. Check commands run from the repository root unless they explicitly select the web workspace. The configuration check is a native provider operation; it must validate current configuration without invoking a legacy runner. Providers must report zero collected cases as failure. A result file is removed before each exchange, so an old result cannot satisfy a new invocation. Requests, responses and summary stay outside the repository; first execution and retries use distinct run directories.

This source boundary does not prove provider availability, parameter expansion, database isolation, namespace behavior, connected delivery, browser behavior, restore, load, physical-device behavior or complete execution. Those checks remain deferred until prerequisites land and execution is separately authorized. A source review is not a release decision.

Each provider exchange has a 3600-second deadline. The dispatcher starts a separate process group, kills that group and reaps the provider on timeout or cancellation, and deletes partial result files. Timeouts are recorded as failures while remaining selections continue; the final summary is failed and the command returns nonzero. Cleanup waits at most five seconds.

Selections publish `check_operations.dependency-pins`, the native equivalent of the retained dependency verification: read both selected runtime requirement files, parse noncomment requirements, and reject missing or out-of-range installed distributions in the selected interpreter before tests. The collection provider must retain per-requirement installed-version details in its execution record. Its response also requires `check_execution`, mapping each operation name to `{operation, exit_code: 0, phase: "before-tests", dependency_fingerprint, requirements}`; `operation` is the exact requested operation object. `requirements` maps each requested file to a nonempty list of `{requirement, installed_version, satisfied: true}` entries. The provider observes installed versions; the dispatcher validates evidence shape, binding, exact declaration coverage and version specifiers. A passed check label alone is insufficient. This operation is proposed and connected execution remains deferred.

Collection now uses two sequential exchanges. Before execution, the collection provider receives `operation: "collect"`, the selection and layout. It returns `schema_version: 1`, the selection's `request_fingerprint`, `complete: true`, the exact requested `lifecycle_policy`, and complete `collected_nodeids`, including all parameter expansions and enabled lifecycle cases. This response is retained separately. The subsequent `operation: "execute"` request includes that response and its `collection_fingerprint`. Execution must return the same fingerprint and exactly that inventory; deleting a case from both execution inventories fails. Summary validation requires the separately retained collection responses. Provider completeness and actual collection remain a connected proof obligation; static definitions alone cannot establish parameter coverage.

Selections also contain `requirement_inventory`, read from every requested requirement file and bound into the request fingerprint. Execution evidence must cover those exact declarations once each. The dispatcher parses each declaration and installed version and evaluates its specifier rather than trusting `satisfied`. Direct references and conditional declarations are unsupported and fail planning rather than bypass validation. Installed versions remain provider observations requiring connected verification.

Every selection publishes `check_operations.python-lint` with operation `native-python-lint-v1`, phase `before-tests`, an explicit runtime configuration, ordered repository-relative targets and executable `argv`. The provider runs that command in the read-only layout before tests. Its `check_execution.python-lint` entry contains the exact operation, zero `exit_code`, phase, dependency fingerprint and `executed_argv` matching the complete requested command. Omitted targets, configuration changes and a pass label without execution detail fail validation. L05 retains distinct Auction factory/module/test/contract and notice module/test scopes; L10 retains all four option roots, option contracts and lane tests. Lint targets participate in source fingerprints. Actual lint execution remains a connected proof obligation.

During each exchange, ordinary termination exits nonzero after removing the provider process group and partial response. Further termination requests are ignored during cleanup; the prior termination handler is restored when the exchange unwinds. The bounded regression replaces process and signal effects.

The dispatcher blocks termination during provider launch and bounded cleanup. Each child restores the prior signal mask before execution. Cancellation first requests termination and waits for nested exchanges to reap their children, then unconditionally removes the separate process group. Pending termination is delivered after the process handle is available for cleanup.

The dispatcher also accepts `--request FILE --result FILE` as the collection provider. It binds selections to the current plan, delegates collect and execute requests to the runtime observation interface, and validates the returned observations before publishing an envelope. Each invocation retains its independent observation request and response in a fresh private execution directory beside the result. Failed exchanges remove the public result. Requests, results and retained execution records use private file permissions.

Shared requests must contain the complete canonical batch and current plan fingerprint. Checks execute once in a private source copy with private copies of locked dependency files, workspace links redirected to the private source tree, offline package settings and private generated outputs. Default dependency-local caches, temporary files and package caches stay inside the private run; dependency directories are never linked back to the checkout. Source links that escape the source tree are rejected before any check runs; internal source aliases are redirected into the private tree. The native configuration operation validates the service manifest against its schema, unique service names and ports, and declared requirements paths and syntax. Shared execution records bind command outcomes to the current fingerprint; no prior build is inferred or reused. Shared checks make no service isolation claim. The installed package and runtime observation interface remain separate prerequisites; local doubles establish envelope behavior, while connected proof remains deferred.

Shared freshness includes the native service manifest and schema, service requirements, root dependency and configuration files, shared source inputs and registered contract fixtures. Changes after the private snapshot invalidate the batch before a successful response is published.
