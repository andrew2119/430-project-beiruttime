# Comparison delivery contract

The composition-ready view uses the existing root provider and canonical page frame, header, fields, buttons, states and placeholders. Selection, unsent reference and exact read operation remain in the mounted component across language changes. No private input or browser persistence is used. Scope changes use the shared read partition. The page contains no transaction controls.

The page data key is `comparison.v1`, operation reference and serialized request, inside the root access scope. This bounded read covers zero to three explicit selections rather than a result collection; pagination and thousand-row totals do not apply. Every chosen identifier remains removable, including an unavailable column.

Ready-before-press and data-on-intent use the shared read definition with `open-only`: no speculative provider call is made. Retained answers use the shared cache, with freshness zero; old facts are hidden during refresh and on errors. First-load placeholders reserve the shared card shape. No new arrival animation is introduced. The root owns first-frame theme, fonts, navigation feedback and motion. Shared route warming/registration and measured per-page size proof remain outstanding with the composition owner; no measured speed or phone claim is made.

Current public source composition is an injected provider, not a seeded endpoint. Missing composition returns pending. Separate connected checks must replace fixtures and rerun sold/hidden, stale, denied, wrong-business, duplicate and timeout/restart cases. The public route entry is deferred: the current shared shell grants its read scope only to the internal area, and the delivery registry accepts only that area. The composition owner must extend the existing shell selection and delivery contract together before mounting this view at /compare. No additional provider or shell is introduced here. Ordinary retries reuse the exact operation and request, including stale expectations; only explicit review clears the selected expectation.

A successful first read pins each returned public revision into a new immutable read request with its own operation reference. Subsequent retries preserve that request and reference. A changed revision stays fact-free until explicit review clears its expectation; the reviewed result is then pinned again. No request body changes under an existing operation reference.
